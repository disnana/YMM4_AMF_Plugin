# RX 6800 XT standalone benchmark (2026-09-14)

## Environment

- GPU: AMD Radeon RX 6800 XT
- AMF runtime: 1.4.37.0
- AMF SDK: 1.5.2.0
- Path: `copy_bgra_efc` (P1)
- Codec: H.264, VBR, balanced, 12 Mbps target / 14.4 Mbps peak
- Input: 1920x1080, 60fps, 900 frames
- Warm-up: separate 120-frame session for each pool size
- Repeats: 5 per pool size

## Results

| Owned texture pool | Median fps | Mean fps | Min fps | Max fps | Median wall time |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 4 | 248.941 | 245.653 | 238.625 | 249.737 | 3615.32 ms |
| 6 | 277.124 | 274.430 | 250.989 | 290.546 | 3247.65 ms |
| 8 | 275.984 | 276.352 | 259.763 | 293.407 | 3261.06 ms |

All 15 MP4 files passed full ffmpeg decode, exact decoded frame count, embedded 16-bit frame-marker order, and BT.709 limited-range metadata validation. Pool 6 improved median standalone throughput by about 11.3% over pool 4 while remaining effectively tied with pool 8, so the plugin default is pool 6.

## Scope

`export_wall_ms` starts with fixture generation/upload and ends after AMF drain and MP4 close. It excludes YMM4 rendering and is not evidence that a complete YMM4 project exports this many frames per second. No claim about speedup over YMM4's standard writer is made until a matched full-project comparison is run.

## Rejected VideoProcessor experiment (not shipped)

An experimental VideoProcessor path was compared with the retained `copy_bgra_efc` path using pool 6. Every run used a separate AMF session, and path order alternated between repeats to reduce order bias. All ten 900-frame outputs passed full decode, exact frame-marker order, and BT.709 limited-range metadata validation.

| Path | Median fps | Mean fps | Min fps | Max fps |
| --- | ---: | ---: | ---: | ---: |
| P1 `copy_bgra_efc` | 247.462 | 237.837 | 200.504 | 274.488 |
| P2 `video_processor_nv12` | 235.990 | 238.211 | 216.454 | 259.507 |

The benchmark source used `BindFlags = 0`, so it could not itself create a VideoProcessor input view and directly exercised the YMM4 compatibility regression. P2's median was about 4.6% lower than P1, and the same 7,259-frame YMM4 export was about 7% slower. The experiment was therefore removed from the plugin, settings UI, native ABI, benchmark CLI, and CI test matrix. These results remain only as a record of the rejected design.

Before the compatibility fix, a direct-input P2 H.264 run at 1920x1080, 60fps and 9000 frames (150 seconds of video) accepted and completed all 9000 frames, passed full decode and exact marker-order validation, and measured 269.571fps. That old path failed with YMM4 textures whose bind flags were not compatible with `CreateVideoProcessorInputView`, so this extended result is historical and does not validate the fixed implementation.

The pre-fix direct-input P2 comparison produced PSNR 35.216dB and SSIM 0.967123 against one decoded P1 output. That combines RGB-to-YUV conversion, chroma sampling, and independent lossy encodes; it is not an original-reference quality score. A simple frame-0 check of 6489 sampled points against calculated BT.709 limited values produced Y/U/V mean absolute errors of 1.07/2.73/3.71 for P1 and 1.19/0.88/1.48 for P2. Original-reference color-difference and VMAF tests for the retained path remain unimplemented.
