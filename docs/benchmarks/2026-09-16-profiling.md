# 診断オプションの検証（2026-09-16）

対象はv0.1.1公開後の開発版です。既存P1のコピー・AMF・MP4処理を維持し、独立した破棄／プロファイリング設定を追加しました。最適化や新版の公開は行っていません。

## 正常系・契約の検証

- CPU側33チェック：既定オフ、ABIサイズと単位、並行コールバック時間の重複除外、空出力、エラー保持、日本語パス、破棄時のネイティブ呼び出し禁止・音声非保持・MP4非生成、UI設定スナップショットなど。
- ネイティブ集計セルフテスト：無効時の非集計、スコープ終了の二重計上防止、4スレッドのカウント・合計・最大値、無効ハンドル。
- ネイティブベンチ4ケース：H.264／HEVC × プロファイル無効／有効。
- 管理側Writer統合4ケース：実際のD2D bitmapを渡し、P/InvokeでAMF出力とプロファイルの取得を実施。26チェックを通過。
- 上記8ケースそれぞれ640×360、60fps、120フレーム、48kHzステレオAAC。全デコード、フレーム枚数・順序、BT.709 limitedメタデータ、A/V長差50ms以内を確認。

実行コマンド：

```powershell
.\scripts\Run-Tests.ps1 -Suite All -Ymm4Directory $amfYmm4Directory
```

CIにはGPU不要のCPU側検証を追加しています。ここに記載する結果はローカル実行の結果であり、GitHub Actions上の実行結果ではありません。

## 観測した調査候補

例として3組目の有効側（全体4595.17ms）では、空きスロット待ち合計0.72ms、AMF投入API合計1362.81ms、CopyResourceのCPU時間合計1.89msでした。出力回収のpoll待機は290回、平均14.53ms、合計4214.85msです。コードで要求しているsleepは1msですが、実際に戻るまでの時間はそれより長くなっていました。

これは出力回収の待ち方を今後調べる手掛かりですが、別スレッドの待機時間は全体時間と重なります。この例ではスロット待ち自体はほぼ発生しておらず、poll待機の合計をそのまま短縮余地とはみなせません。フレーム生成・uploadもベンチ全体に含まれるため、YMM4やAMFハードウェアの限界を示すものではありません。待機や同期の挙動は変更していません。

## 残る確認

YMM4実アプリでの新しいチェック項目の操作、破棄後のホスト動作、同じ実プロジェクトの通常／破棄比較は未実施です。比較手順は[プロファイリングガイド](../profiling.md)を参照してください。キャンセル・device removal・プロセス強制終了、GPUタイムスタンプによる内訳、長時間の計測負荷、元映像に対する画質・音声同期の厳密な評価も別途必要です。
