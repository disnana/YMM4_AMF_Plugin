# AMF投入スレッド・専用デバイス分離: 実装と検証結果

## 結論

**2つの実験オプションを実装したが、この隔離試験では速度改善を確認できなかった。初期値は両方OFFを維持する。**

- AMF投入の専用スレッド化だけでは、通常の合成入力でほぼ同速。描画量を増やしても全体時間の短縮は確認できなかった。
- 同一GPU上の専用D3D11デバイスへ分離すると、短い試行では追加のコピー・同期・初期化により遅くなった。9000フレームの試行では差が小さくなるが、速度上の優位は示せていない。
- プールを32面に増やして両方ONにした条件では、標準プリセットの中央値が406.69→354.08 fps。キューを増やすだけでは改善しない。
- 113本、118,020フレームの正常出力を全デコード・順序検査。比較した20本では、同じ画質設定内の復号画素が一致した。速度のために圧縮設定を変えてはいない。
- 高品質は削除せず、通常は標準を推奨する理由をUIへ表示した。2素材だけで高品質の効果を一律否定しない。

これは**実AMFプラグインDLLを使った隔離ハーネス**の結果であり、実YMM4プロジェクト全体の出力速度・安定性を保証しない。今回MFとの比較は再実行していない。[以前のMF・画質比較](2026-09-18-mf-actual-writer.md)と別の試験である。

## 実装した境界

| モード | AMF投入 | デバイス | プラグイン内のGPUコピー |
| --- | --- | --- | ---: |
| base | WriteVideo呼出元 | 元デバイス | 1 |
| worker | 専用スレッド・有界キュー | 元デバイス | 1 |
| device | WriteVideo呼出元 | 同一adapterの専用デバイス | 2 |
| both | 専用スレッド・有界キュー | 同一adapterの専用デバイス | 2 |

借用した描画面ではなく、所有プールへコピーした面だけをキューに渡す。プール・キューは有界。既存のQueryOutputスレッドは全条件で動くため、baseも全処理が直列の実装ではない。専用デバイスでは共有面1枚とkeyed mutexを使う。コピー数にAMF内部の変換やYMM4 v2経路の中間コピーは含めない。

従来回収モードでのAMFSurface再利用は、SubmitInput復帰と出力通知の両方を待つようにした。出力通知が先着しても、投入処理中のSurfaceを次フレームが変更しない。最終測定はこの修正後のDLLに統一した。[所有権・終了順序・設定の詳細](../pipeline-experiments.md)

## 条件と計時

- GPUは実デバイスから取得したRX 6800 XT。既存調査と同じRyzen 9 5900XのPC。native試験ログのAMF runtimeは1.4.37.0、SDKは1.5.2.0。
- YMM4 4.56.1.1環境のGraphicsDevicesを隔離apphostで使用。実YMM4プロジェクト・インストール先・設定は変更していない。
- 主測定: H.264、1920×1080、60 fps、900フレーム。128個の移動矩形とフレーム順序マーカー、440 Hz / 48 kHz stereo音声。
- AMFはVBR target 12 Mbps / peak 14.4 Mbps。各比較内でプリセット、bitrate、回収、出力待機、プール枚数を固定。
- 通常群は既存の入力解放通知・出力待機改善をON。legacy群だけ両方OFF・6面。今回追加した2つの設定とは別軸。
- 4条件を各4回、ラウンドごとに全順序を反転。計時中には別のベンチや検証デコードを並走させない。プロファイルONは別試行。
- `export_ms`は最初の描画からDispose完了まで。constructorは別測定、AMF遅延初期化は最初のフレームに含む。フレーム供給終了後の状態取得もexport時間に含む。
- fpsは各試行の完了fpsの中央値。秒数もそれぞれの中央値。外れ値を除外していない。

## プロファイルから分かったこと

別の900フレーム診断試行、標準16面。CPU wall-time平均ms。非同期区間と入れ子区間があるため列を合計しない。

| 区間 | base | worker | device | both |
| --- | ---: | ---: | ---: | ---: |
| 所有面の空き待ち / frame | 1.9211 | 1.9870 | 1.7037 | 1.8246 |
| コピー・bridge呼出 / frame | 0.0071 | 0.0096 | 0.2832 | 0.2911 |
| SubmitInput呼出 | 0.1757 | 0.1872 | 0.1294 | 0.1584 |
| QueryOutput呼出 | 2.3390 | 2.3548 | 2.3650 | 2.3786 |
| 圧縮bitstreamのmux / frame | 0.0144 | 0.0144 | 0.0165 | 0.0166 |
| 音声Write / callback | 0.1222 | 0.1181 | 0.1194 | 0.1193 |

CopyResourceだけのGPU実行時間ではなく、専用デバイスの列にはbridge同期も含む。GPU timestampで2コピーとmutex待ちを分離した測定はまだない。

16面では全モードのSubmitInputリトライが0、入力面peak16。workerだけの場合、投入キューpeak4、滞在平均0.048 msだった。面の空き待ちは残っており、投入スレッドを追加しても下流の処理能力は増えていない。

32面ではbaseも133回リトライし、既存の`1 ms` sleep呼出は実測平均12.913 ms、合計1717 ms。bothでは151回、平均14.743 ms、合計2226 ms、投入キューpeak21 / 滞在平均45.764 msだった。worker単独も133回、キューpeak25 / 滞在平均41.838 ms。**待ちの場所が呼出元からworkerと所有面待ちへ移った**と解釈できる。bothの悪化を追加コピーだけで説明する根拠はなく、リトライ待機方針も次の切り分け対象となる。

全97ハーネス試行でGen0/1/2の回数増分は0。タイミング群のmanaged allocationは約0.394 MB/900f、最大約0.406 MB。ハーネスの計測配列等も含み、C++/ドライバーの確保量ではない。GC pauseそのもの、GPU使用率、Video Codec使用率は未測定。CPU時間も記録したが、CPU使用率を上げること自体を高速化の指標にしない。

## メモリ・終了・出力整合性

9000フレーム、標準16面、profile ON、各1回。動画時間は150秒だが実行時間は約22秒で、数時間の耐久試験ではない。GPUメモリはIDXGIAdapter3のプロセス会計を60フレームごとにサンプルしたもの。

| モード | 完了fps | 60〜9000fのLocal範囲 MiB | NonLocal範囲 MiB | Dispose直後Local MiB |
| --- | ---: | ---: | ---: | ---: |
| base | 415.99 | 156.94–156.94 | 56.13–56.13 | 149.69 |
| worker | 415.79 | 157.19–157.19 | 56.13–56.13 | 149.94 |
| device | 413.97 | 178.75–178.75 | 59.70–59.70 | 22.00 |
| both | 414.57 | 178.75–178.75 | 59.70–59.70 | 22.00 |

この期間のサンプルでは増加なし、全モード9000入力/9000出力、invalid event 0、終了時の使用面・投入キューは0。単発の診断値を4回中央値の速度表に混ぜない。

4K/180fの追加診断では、128面要求が画素量1 GiB目安によって実効32面へ制限された。Localピークはbase 1094.19 MiB、worker 1095.00 MiB、device 1162.75 MiB、both 1163.38 MiB。1 GiB目安は総VRAMのハード上限ではない。専用デバイスでは共有面とデバイス/ドライバー等の費用が追加される。

同一デバイス経路のDispose直後には4Kで約1070 MiBが残った一方、専用デバイスでは約69 MiBになった。前者はホスト相当のデバイスをまだ保持している段階、後者は専用デバイス自身を破棄した段階であり、条件が異なる。解放完了やリークの有無をこの1点だけで断定しない。製品から借用デバイスをClearState/Flushして解放を強制する変更もしていない。

### 合格した試験

- ハーネス97本 / 116,100f: 全デコード、全フレーム順序マーカー、サイズ、fps、音声形式・長さを検証。音声開始差0 ms、長さ差8.000〜18.667 ms。リップシンクの検証ではない。
- native16本 / 1,920f: H.264/HEVC × 入力解放回収ON/OFF × 4モード。全デコード・順序・BT.709 limitedメタデータ・音声長検査成功。
- 96回のFinalizeなしDestroy: 0/1/8入力、H.264/HEVC、回収・分離の組合せ。各Destroyの制限5秒、隔離子プロセスの上限30秒以内で終了。
- 保護されていない借用デバイスでworker単独を拒否。専用デバイスとの併用は成功し、借用デバイスの保護設定と描画先を変更しないことを検査。
- 不正寸法の最初のエラーをFinalizeでも保持し、codec headerの二次エラーで上書きしないことを検査。
- 古いnative DLLとの混在をworker/device/bothの3条件で拒否。フレーム投入やMP4生成前に明示エラー。
- Unit: managed 248チェック、画質比較契約18件、nativeプロファイル/出力待機/回収/4096件並行キュー/Surface再利用条件。Release build警告0・エラー0、追加PowerShell構文検査成功。

### 画素の確認と高品質の扱い

第1巡のbalanced 8本、quality 4本、render64 4本、legacy 4本を全フレームYUV420pへ復号し、各群のSHA-256が一致した。標準・legacy・render64は`aadc1646…1028d6`、高品質は`33569112…366714`。完全な値と対象ファイルは`decoded-frame-hashes.json`に保存。新しい分離オプションによる画素変更は、この入力では検出されなかった。

以前の共通参照による2素材では、標準→高品質のPSNR差は約+0.0068 / +0.0291 dB。以前の合成比較で約2.2倍、今回の標準16/baseと高品質16/baseでは約2.4倍の処理時間だった。効果の小さい素材で大きな時間を払う可能性を明示し、UIを「標準（通常はこちらを推奨）」「高品質（低速・画質差を要確認）」へ変更した。プリセット値・初期値・保存値は変更していない。

「全素材で高品質が無意味」「標準がMF品質100と同等」という結論ではない。MFとAMFでは色変換・圧縮条件も異なり、以前の画質比較の順位は素材によって逆転している。

## 次に調べる範囲

1. 実YMM4プロジェクトの同一範囲で新オプションOFF/ONを順序反転比較する。実際の描画デバイスのthread protection検査、取消、繰り返し出力も含む。
2. 32面等で見えたSubmitInput入力満杯時の待機を、品質を変えない別実験として調べる。busy-spinでCPUを浪費する案を既定にはしない。
3. 専用デバイスの遅いDisposeをprofile付き反復で分離する。GPU timestamp、実GPU copy/convert、AMF内部queue depth、複数時間/device lostは未検証。
4. MFとの画質差は実効encoder propertyのreadbackと共通NV12入力で、色変換と圧縮を切り分ける。今回の分離実装で画質差が解決したとは扱わない。

現段階では新オプションのデフォルト有効化、Rust化、無制限のtexture確保を推す結果ではない。
