# 所有テクスチャ増量・回収方式の実機比較

## 結論

RX 6800 XT / Ryzen 9 5900Xでは、標準プリセットの従来6枚から8〜16枚への増量に効果があった。しかし、既存の出力待機最適化をONにすると6〜16枚でほぼ同じ上限に届く。32〜128枚は速度を伸ばさず、メモリと1回のWriteVideo停止時間を増やす。

高品質プリセットは6〜128枚とも約168 fpsのまま。プールを増やせばMFとの差が解消する、という結果ではない。圧縮設定は今回変更していない。

入力解放通知による回収だけの改善は小さい。「所有texture数」「入力寿命」「出力回収待機」「AMF投入待機」は別々に扱う必要がある。

## 実装した範囲

- 所有プールの選択肢: 4 / 6 / 8 / 16 / 32 / 64 / 128枚。16枚以上は実験表示。
- **既定6枚、回収実験OFFのまま**。品質・RC・GOP・コピー回数は変更しない。
- 増量時は幅×高さ×4×枚数を目安1 GiBに制限。1080pは128枚、4Kは32枚、8Kは8枚になる。従来の4〜8枚は維持する。alignmentやAMF内部を含む総VRAM制限ではない。
- ネイティブ／管理側の双方で制限し、実効枚数・最大使用数・入力枯渇回数・未回収予算枯渇回数を記録する。
- 入力解放回収ONでは未回収上限が実効枚数の2倍。OFFでは入力textureと圧縮出力の寿命が結び付くため実効枚数と同じ。今回の枚数比較は、この上限も一緒に変わる。
- 古いネイティブDLLとの組み合わせで増量が黙って8枚へ丸められないよう、新しい状態取得APIで実効枚数を確認する。
- 無制限確保、投入専用スレッド、専用D3Dデバイス、色変換器の変更は実装していない。

## 条件と証跡

Windows 26200、.NET 10.0.12、AMDドライバー32.0.21045.5002。実YMM4 4.56.1.1の公開描画デバイスと、ビルドしたAMF writer DLLを隔離プロセスで使用。1080p60、900フレーム、同じD2D図形・フレームID、H.264、VBR 12,000/14,400 kbps、48 kHz stereoテスト音声。GPU直渡しON。YMM4プロジェクト全体の速度ではない。

通常計時はプロファイルOFF、各条件4回、全条件列を正順／逆順／正順／逆順で実行。検証デコードは計時後に行った。`export_ms`は描画開始からDispose完了まで、別途writer constructor込み時間も保存。AMFの遅延初期化は最初のWriteVideoに含まれる。

ローカル証跡は`artifacts/runs/texture-pool-20260918/`:

- `balanced/`: 6種類の枚数×4方式×4反復 = 96出力。
- `quality/`: 4種類の枚数×2方式×4反復 = 32出力。
- `profile/` / `quality-profile/`: 区間時間、実効プール、メモリの別実験27出力。
- `long/`: 9,000フレームの3出力。動画長150秒、実行時間約22秒。数時間の耐久試験ではない。
- `4k128/`: 128枚要求が32枚に制限される4K/180フレーム確認。

- `decoded-frame-hashes.json`: 初回の全32条件で復号画素を照合。

## 標準プリセットの速度

単位は完了fpsの4反復中央値。各列の違いは回収オプションのみ。

| 枚数 | 両方OFF | 入力解放回収だけON | 出力待機最適化だけON | 両方ON |
| ---: | ---: | ---: | ---: | ---: |
| 6 | 370.61 | 371.22 | 397.28 | 406.24 |
| 8 | 404.41 | 405.14 | 407.03 | 407.75 |
| 16 | 406.61 | 405.19 | 407.21 | 407.22 |
| 32 | 405.78 | 405.49 | 407.09 | 406.94 |
| 64 | 404.46 | 405.06 | 406.11 | 406.20 |
| 128 | 404.07 | 404.25 | 404.93 | 404.96 |

従来6枚→16枚・両方ONは中央値で約9%の時間短縮／約10%のfps向上。ただし6枚・両方ONも406.24 fpsなので、その向上を全て増量や入力解放回収の効果にしてはいけない。8枚と16枚の差はごく小さく、優劣を断定しない。

外れ値も保持した。例えば64枚・待機だけONは2,211〜4,652 ms、128枚・待機だけONは2,219〜5,823 ms。長いrunはDispose区間がそれぞれ2,475 ms／3,643 msだった。GCはいずれも0回。これだけで原因をVRAM不足やGPU同期と決めない。別の128枚プロファイルでもMP4終了区間の359.9 msを観測したが、同じ原因と断定できない。

## 1フレームの待ちが移動した

標準の別プロファイルrun:

- 6枚・従来: pool wait合計約1,990 ms、投入再試行0回。
- 16枚・両方ON: pool wait合計約1,715 ms、投入再試行0回。
- 128枚・両方ON: pool waitはほぼ0だが、投入再試行133回、retry sleep合計1,747 ms。1回平均13.13 msだった。

32枚以上は同時使用textureが最大17枚に留まった。これは「投入準備中」を含むプラグインの使用数であり、AMF内部キュー容量が厳密に16と証明したわけではない。ただし空きtextureがあってもSubmitInput側で止まっていることは確認できる。

通常runのWriteVideo呼出時間（各runの分位点を取り、その中央値。最大は全runの最大。初期化を含む）:

| 設定 | p50 ms | p95 ms | p99 ms | 最大 ms |
| --- | ---: | ---: | ---: | ---: |
| 6枚・従来 | 0.15 | 13.97 | 14.30 | 44.00 |
| 16枚・両方ON | 2.17 | 2.33 | 2.39 | 44.50 |
| 128枚・両方ON | 0.20 | 13.44 | 13.95 | 79.20 |

p50や枯渇回数だけなら大容量が良く見えるが、バッチ的な投入待ちに移り、全体速度は伸びていない。分位点・終了処理まで一緒に見る必要がある。

## GPUメモリと終了時の解放

標準・両方ON、1080p、60フレームごとの診断サンプル最大:

| 枚数 | DXGI Local使用量 MiB |
| ---: | ---: |
| 6 | 71.19 |
| 8 | 88.44 |
| 16 | 156.94 |
| 32 | 292.94 |
| 64 | 564.94 |
| 128 | 1,108.94 |

これは[QueryVideoMemoryInfo](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiadapter3-queryvideomemoryinfo)による当該プロセス・node 0のLocal会計。全GPUの使用量でも連続観測した真のピークでもない。画像の理論画素量とも区別する。4Kで128枚要求したrunは実効32枚、Localサンプル最大1,094.19 MiBだった。

9,000フレームでは6枚・待機ONが416.12 fps、16枚・両方ONが416.15 fps、128枚・両方ONが415.61 fps。初期確保後の使用量は今回のサンプルでは横ばいで、連続的な増加はなかった。数時間・同一ホストでの連続エクスポート・device lostは未検証。

Dispose直後にはLocal使用量が多く残ったため、別の隔離実験も行った。`artifacts/runs/texture-pool-cleanup-20260918/`の180フレーム出力で、計時終了後に200 ms待機→そのテスト自身のcontextへ一度だけFlush→200 ms待機した:

| 枚数 | Dispose後200 ms | 最後のFlush後200 ms |
| ---: | ---: | ---: |
| 6 | 64.44 MiB | 13.44 MiB |
| 128 | 1,101.69 MiB | 13.69 MiB |

これはD3D11の遅延解放と整合する。即時のメモリ会計残量だけでリークとは扱わない。[MicrosoftのFlush説明](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-flush)にも遅延破棄とFlushの関係がある。**製品プラグインにはこのFlushを追加していない**。毎フレームFlushを入れる改善でもない。共有されたYMM4デバイスへ安易にClearStateすることは避ける。

## CPU、ライブラリ、MFとの分離設計

現在のMF DLLも再照合した。SHA-256は`669F9FD2490EEC545CD0E7E8EBC2B2090DD6DAACDB419EB7D2412DD3CA51C23F`で、[前の実DLL調査](2026-09-18-mf-actual-writer.md)の対象と一致する。

| 観点 | 標準MF | 現在のAMF |
| --- | --- | --- |
| 入力画像の所有・寿命 | 2回のGPUコピー、TrackedSampleで返却 | 1回のGPUコピー。従来の出力回収／実験の入力解放回収 |
| D3Dデバイス | writerが新しいGraphicsDevicesを所有。shared/keyed mutex経由で渡す | YMM4から受け取ったdeviceをAMF InitDX11へ渡し、ImmediateContextを共有 |
| 変換／圧縮 | 実行時にVideoProcessor→AMDh264Encoderを確認 | amfrt64.dllのAMFVideoEncoderVCE_AVCへBGRA入力。内部変換は別途切り分けが必要 |
| 投入側の待機 | WriteSample後のMF/MFT内部処理と次の描画を重ねられる。ただしbridge自体はlockとmutexで直列 | CopyResource＋SubmitInputはWriteVideoの呼出スレッド。INPUT_FULL再試行もそこで待つ |
| 出力の回収 | MF内部で管理 | QueryOutputとbitstream処理は専用スレッド。ファイル書き込みも別スレッド |

MF側の根拠は`MFVideoFileWriter`のconstructor / CreateSinkWriterAttribute / WriteVideoGpu、`EncoderFrameBridge.AcquireSample` / BuildTrackedSample。AMF側は`AmfVideoFileWriter.WriteVideo`、`InitializeAmfEncoder`、`EncodeTexture` / `EncodeRecycledTexture`、`StartOutputThread`。

さらに実Plugin DLLの`GraphicsDevices` / `D3DDevices`まで辿った。`GraphicsDevices`は`new D3DDevices()`を呼び、そのconstructorがD3D11CreateDeviceを実行するため、単なる同一deviceの別ラッパーではない。各deviceのmultithread protectionはON。`D3DDevices.Dispose`はClearState→Flush→所有リソース破棄を行う。MFはこの専用deviceを処分できるが、AMFは借用したYMM4 deviceを処分できない。これは終了時のメモリ解放方針の差でもある。ただしMFの終了後VRAMを今回対照測定したわけではない。

**「意図的にコピーして分離し並列化する」はMFの設計として確認できる。しかし「それが現在のMFとAMFの速度差の主因」は未証明。** AMFも寿命と回収処理は既に分離している。一方、AMFへの投入が詰まるとYMM4の次フレームへ戻れない、という境界は残る。別DLLであることは、別プロセスや別GPUデバイスであることを意味しない。

前の同じ合成入力・4反復のプロセスCPU計測を読み直すと、MF GPUのCPU時間中央値1,437.5 ms、AMF高品質929.7 ms、AMF標準335.9 ms。各runでCPU時間÷出力時間÷24論理CPUを計算した中央値は順に2.44% / 0.72% / 0.58%だった。MFはCPU処理量が多いが、24スレッドを使い切って速い結果ではない。この数値はYMM4プロジェクト全体やシステム全体の使用率ではなく、MFの別プロセスFFmpeg AACも含まない。設定の違う経路をCPU効率だけで順位付けしない。

次の比較候補は、画質・RC・プール上限を揃えたまま、(A)投入専用スレッド＋bounded queue、(B)専用D3Dデバイス＋安全なGPU受け渡し、(C)明示的なGPU色変換、を**一つずつ**追加すること。Aで上流を進められてもGPUの定常処理能力自体は増えない。Bもmutex／追加コピーで遅くなる可能性がある。今回の高品質が約168 fpsから動かなかった事実と、前回MFの速度設定だけで大きく変化した事実を無視して、デバイス共有だけを原因にしない。
