# MF方式 GPU VideoProcessor → NV12 → AMF 実験（2026-09-18）

## 結論

標準MFで確認した「GPU上でRGBをNV12へ変換し、エンコーダー所有面の寿命を入力元から分離する」構造を、既存AMF writerを壊さない既定OFF経路として実装した。RX 6800 XTではH.264/HEVCとも正常に動作したが、現行BGRA→AMF経路より速くならなかった。このため既定OFFを維持し、安定経路の置き換えにはしない。

1080p H.264 balanced/VBR、12 Mbps、1,200 frames、pool 6のAB/BA各4回では、現行BGRAが中央値286.61 fps、新NV12経路が282.44 fps（新経路が約1.45%低速）だった。追加探索で最良だったNV12 pool 8と現行BGRA pool 6を600 framesのAB/BA各4回で比較しても、中央値255.42 vs 256.49 fps（約0.42%低速）で、優位性は確認できなかった。

## 実装した経路

```text
YMM4 BGRA/RGBA texture
  -> CopyResource（所有RGB互換テクスチャ、BindFlags=0）
  -> D3D11 VideoProcessorBlt（BT.709 full RGB -> BT.709 limited NV12）
  -> 所有NV12 texture pool
  -> AMFSurface(DX11 native)
  -> AMF H.264 / HEVC encoder
```

旧P2のようにYMM4テクスチャへ直接VideoProcessor input viewを作らない。所有RGB互換テクスチャを1枚挟むことで、YMM4側テクスチャのBindFlagsから入力ビュー互換性を切り離した。CPU readback、`Map`、CPU色変換、毎フレームのtexture/view確保、`Flush`は追加していない。NV12 poolとoutput viewは初期化時に作成し、既存のbounded poolと回収機構で再利用する。

専用D3D11デバイス実験との組み合わせは未実装で、黙って経路を変えず初期化エラーにする。既存creator ABIは変更せず、`AmfCreateWithMfStyleNv12`と`AmfGetMfStyleNv12Status`を追加した。

## 実機と検証条件

- GPU: AMD Radeon RX 6800 XT
- AMF runtime: 1.4.37.0
- AMF SDK headers: 1.5.2.0
- H.264 / HEVC
- SDR BT.709 limited, yuv420p
- balanced、VBR
- 640x360 smoke: 120 frames
- 1920x1080 timing: 600または1,200 frames
- 性能測定はdebug log/profileをOFF、順序反転
- `artifacts/runs/mf-style-nv12-*`に実行JSONと出力を保存

## 正しさ・組合せ検証

- ネイティブH.264/HEVC smoke: 各120/120 frames、変換失敗0、デコード・順序・BT.709 limited合格。
- managed writer → P/Invoke → native → AMF: 864 checks合格。
- 新経路32出力を別途ffmpegで検証: H.264/HEVC、GPU直渡しON/OFF、入力回収ON/OFF、待機ON/OFF、profile ON/OFFの全出力で120 frames、順序、BT.709 limited、AAC音声を確認。
- Unit/ABI: managed 264 checks、ネイティブprofile/output-wait/input-recycling/pipeline self-test合格。

## プールと回収

NV12経路を600 frames、順序反転2回で測定した。

| pool | 平均fps | 範囲 |
|---:|---:|---:|
| 4 | 237.67 | 235.48–239.87 |
| 6 | 272.16 | 268.22–276.10 |
| 8 | 277.86 | 272.98–282.74 |
| 16 | 273.98 | 269.40–278.55 |

4枚は明確に不足した。6〜8枚で回復し、16枚へ増やしても伸びなかった。実験ON時もユーザー指定poolを尊重し、自動で8枚へ変更しない。

NV12経路内で従来回収と入力解放回収を600 framesのAB/BA各4回で再比較した結果は、従来283.11 fps、入力解放回収279.72 fps（約1.2%低速）。入力寿命分離は正常動作したが、この条件では速度向上にならなかった。長い1,200-frame試行は途中でマシン全体が約289→237 fpsへ低下したため、性能根拠から除外した。

## 画質指標

同じ300枚の未圧縮BGRA生成フレームから、現行BGRA経路と新NV12経路を同一AMF設定で出力した。別途FFmpegでBT.709 limited yuv420pへ変換したlossless FFV1を共通基準とした結果:

| 経路 | PSNR average | SSIM mean | SSIM p05 | ファイルサイズ |
|---|---:|---:|---:|---:|
| 現行BGRA→AMF | 38.554 dB | 0.976935 | 0.974313 | 2,652,566 bytes |
| VideoProcessor NV12→AMF | 37.325 dB | 0.980651 | 0.965971 | 2,659,913 bytes |

新経路は平均SSIMのみ高く、PSNRと下位5% SSIMは低かった。ソフトウェア色変換した基準との距離であり、視覚的優劣やMF同等画質を確定する結果ではない。色変換アルゴリズム差と圧縮差が混在するため、実写・文字・グラデーションでの目視評価は別途必要。

## 判断

MFが速い理由の一部である「CPU readbackを避ける」「所有面で寿命を分離する」「GPU変換とencodeを重ねる」は既存AMF経路にも既に入っている。今回さらにMFと同じ方向へNV12変換を外出ししても勝てなかったことから、残る差を単純なRGB→NV12変換場所だけに帰属できない。

次に価値があるのは、標準MFとAMFを同じYMM4描画負荷・品質・bitrateで実出力し、GPU timestampでVideoProcessor/Copy/encodeを対応付けること。CPU/C++/Rustへの書き換えは、今回のGPU変換区間が支配的でないため優先しない。
